# Session 1 - Core Math & Modularization v1.0

## 1. Core Mathematical Corrections
- **Herringbone Tessellation:** Adjusted the geometric generation of herringbone layouts. The original approach relied on a uniform grid with alternating angles, causing overlapping. This was replaced with a coordinate system based on interlocking staircase basis vectors (L, L) and (-W, W).
- **Vertical Alignment Offset:** Corrected a sign error in the vertical tile positioning (baseY2 calculation) that was causing tiles to miss the staircase alignment and leave open gaps.
- **Grid Centering:** Fixed an alignment offset issue where standard rectangular tiles were anchoring from their center rather than their bottom-left corner, which previously caused incorrect tile counts.

## 2. Codebase Modularization
- **State & Export Separation:** Moved the verbose jsPDF export and document styling code out of App.tsx and into a dedicated pdfExport.ts utility file.
- **UI Sub-components:** Modularized SidebarControls.tsx into a structured directory of specialized panels (WallSetupPanel, TileSpecsPanel, ColorControlsPanel, FeaturesPanel).
- **Canvas & Math Decoupling:** Separated drawing commands from coordinate math. The logic was split across geometry.ts (vertices/offsets), generator.ts (tile array loops), analytics.ts (sliver calculations), tileRenderers.ts (individual shape drawing paths), and canvasPainter.ts (orchestration).

## 3. Feature Extensions
- **Wall Extensions:** Implemented support for non-standard, multi-rectangle wall shapes (such as L-shapes or bump-outs) using a unified canvas path and combined boundary logic.
- **Stencil Masking:** Added a stencil mode to SubAreas, allowing accent panels to be dragged outside the main wall boundaries while clipping their tile rendering strictly to the combined wall perimeter.
- **New Geometry Options:** Added support for Equilateral Triangles, Pickets (elongated hexagons), Scallops (fish scale), and Octagon & Dot composite layouts.
- **Material Estimation Tools:** Integrated an overage/waste factor calculation and a "Mosaic Sheets" toggle that calculates materials in standard 12x12 sheet units rather than individual piece counts.
- **Draggable Smart Snapping:** Programmed magnetic snapping thresholds so that Wall Extensions and SubAreas lock to the main wall boundaries, its horizontal/vertical center lines, and to other nearby accent panels.
- **JSON Save and Load:** Implemented file-based saving and loading by stringifying the React state configuration into a downloadable JSON file.

## 4. Performance & UX Polish
- **Calculation Debouncing:** Converted the heavy comprehensive statistics calculation from a synchronous useMemo call into a debounced useEffect hook with a 300ms delay, reducing CPU load during active dragging.
- **Perimeter Dimensions:** Updated the dimension rendering logic to trace the outer edge of complex wall boundaries, preventing redundant dimensions on uniform walls and correcting text clipping on the canvas edges.
- **Zero-Value Exception Handling:** Added a safety check at the top of the generator to prevent divide-by-zero infinite loops (and subsequent browser freezes) when width or height inputs are cleared.

# Session 3 - Versailles Pattern & Multi-Color Stripe Logic v1.3

## 1. Versailles Pattern Implementation
- **The Problem:** The initial 12-piece block generation created prominent, continuous horizontal and vertical grout lines across the layout because the tiles were constrained to a flat-sided block.
- **The Solution:** We mapped out a custom 12-piece interlocking matrix based on a 6x6 grid. By shifting specific tiles to "overhang" the right and bottom boundaries of the grid, we created matching "holes" on the top and left boundaries. When repeating, the blocks now slot into each other like puzzle pieces, successfully breaking all continuous seams.

## 2. V1-V4 Tile Color Variation
- **The Concept:** To mimic real-world tile shade differences, we planned a system using the V1-V4 grading scale.
- **The Implementation:** We designed a deterministic, coordinate-seeded pseudo-random function. Instead of using Math.random(), which causes the tiles to flicker during canvas panning, the shift in HSL lightness/saturation is calculated using the tile's stable center coordinates. This provides a consistent, natural-looking color variation.

## 3. Multi-Color Layout Engine
- **UI/UX Flow:** We designed an always-on "Color Pattern" dropdown. Selecting structured patterns (like Checkerboard or Stripes) displays the exact number of required color pickers, while selecting "Random" displays an "Add Color" button allowing the user to dynamically build a palette of up to 6 colors.
- **Stripe Debugging:**
  - **Grout Drift:** We resolved an issue where stripes doubled up periodically due to dividing raw coordinates by tile size. The math was updated to divide by the tile step (tile dimension + grout width) using Math.round().
  - **Zero-Line Mirroring:** We fixed a bug where the stripes mirrored backwards across the zero-coordinate line (creating a double-wide center stripe) by replacing Math.abs() with a continuous, negative-wrapping modulo formula.
- **Random Blend:** We reviewed the visual output of the randomizer and confirmed the current organic, slightly clustered scattering meets the illustrative goals of the application.

## Architectural Assessment: Multi-Factor Authentication (MFA)
- **Is it worth it?** Yes, but strictly as an optional feature for standard users. While protecting user design assets and AI credits is highly valuable, forcing MFA upon registration creates significant signup friction. It also introduces a manual support burden (assisting users who lose their authenticator devices or backup codes).

- **The Admin Exception:** While MFA should remain optional for regular users, it should be mandatory for Admin accounts. Securing the administrative credentials is the single most effective way to protect your self-hosted backend.

# Addendum to Session 31: Strategic Technical Debt & Future Roadmap Considerations

As the WildVision CAD and rendering suite continues to expand in commercial complexity, the following three architectural areas have been identified as high-priority risks. These items should serve as the blueprint for our future stability and optimization sprints:

## 1. Schema Fragility & JSON Backwards Compatibility
* **The Risk:** Pushing full, complex Zustand state snapshots (coordinates, custom pattern arrays, color palettes, and panel configurations) directly to Supabase as single JSONB payloads means our save-file schema is highly volatile. A minor change in how custom patterns or sub-area boundaries are structured in the code can instantly break historical client files or cause them to crash upon loading/hydration.
* **Future Mitigation:**
  * Implement a formal **Schema Versioning** header (e.g., `schemaVersion: 4.31`) inside every saved JSON payload.
  * Develop a lightweight **Migration/Upgrader Utility** inside `projectSlice.ts`. When a project is loaded, the store should inspect the version header, route it through sequential, incremental upgrade functions (e.g., `migrateV3ToV4`), and normalize the data payload before mounting it into active working memory.

## 2. GPU Memory Tracking & WebGL Canvas Lifecycle
* **The Risk:** Procedural rendering of multiple 2048px off-screen canvas buffers (`canvas` and `bumpCanvas`) and WebGL textures inside React hooks can cause serious GPU memory fragmentation over long design sessions. This is especially critical on memory-constrained mobile browsers and older iPads, where WebGL can suffer silent context loss, turning the 3D diorama completely black.
* **Future Mitigation:**
  * Ensure all text and numeric inputs for tile dimensions are heavily debounced in the UI, preventing rapid-fire, continuous texture-baking cycles during active typing.
  * Implement a strict **Texture Lifecycle Audit** inside `useTileTexture.ts` to guarantee that all cloned textures and canvas references are completely unlinked, disposed of (`.dispose()`), and garbage-collected immediately upon unmounting or re-generation.

## 3. Automated Geometry & Layout Regression Testing
* **The Risk:** Currently, 100% of our testing is manual. Because our vector drafting physics (curved segments, apex hinges, and segment extrusion) and layout generation loops contain highly complex coordinate mathematics, a minor change in `geometry.ts` can cause silent regressions in layout generation (e.g., causing herringbone tiles to overlap on walls with non-standard dimensions or custom extensions) that won't be caught until a client is on a live job site.
* **Future Mitigation:**
  * Set up a lightweight, headless automated unit-testing suite (using a framework like **Vitest**).
  * Write mathematical assertion tests for core utilities in `geometry.ts` and `generator.ts` to verify that tile coordinates, boundary clipping paths, and vertex snapping projection outputs remain correct across a standard set of wall-profile permutations (orthogonal walls, arched alcoves, and L-shape extensions).

 # Addendum 2 to Session 31: Procedural Material Scale & Rotation Upgrades (v4.31)

To achieve absolute real-world color and scale accuracy for imported textures, the 2D canvas texture-baking pipeline has been overhauled. This update permanently resolves visual repetition, "texture-swimming," and interior wrapping seams across all tile sizes.

---

## 1. Real-World Texture Scale Mapping (CAD Alignment)
* **The Upgrade:** Implemented physical scale metadata (`realWorldWidth` in inches) for all texture assets. The baking engine now calculates texture scaling relative to the active viewport scale (`pixels per CAD inch`) rather than the raw pixel dimensions of the canvas.
* **The Benefit:** Natural stone and wood grain textures are now mathematically locked to their real-world physical dimensions. The texture scale remains perfectly consistent, preventing the patterns from stretching, shrinking, or "swimming" when the main wall's dimensions are resized.

---

## 2. Local Coordinate Anchoring & Clamped "Slab-Cuts"
* **The Upgrade:** Rewrote how pattern transformation matrices are mapped to individual tiles. Instead of locking the texture pattern to the global canvas origin `(0, 0)`, the origin is translated directly to each tile's geometric center (`pCenter`).
* **The Benefit:** This shifts the repeating boundaries of the texture completely outside the tile's coordinates. Tiles smaller than the texture act as "cookie cutters," carving out a single, seamless, continuous chunk of the image with mathematically guaranteed zero-seam lines.

---

## 3. "Enlarge-Only Cover" Scaling
* **The Upgrade:** Integrated an automatic scaling clamp (`Math.max(requiredScale, 1.0)`) into the texture transformation matrix.
* **The Benefit:** 
  * Tiles smaller than the texture remain at a clean 1:1 physical scale, carving out random, un-scaled pieces of the slate.
  * Oversized tiles (larger than the texture) are scaled up *just enough* to cover their face, protecting them from ever revealing repeating edge lines.

---

## 4. "Diagonal Safeguard" Organic Rotation
* **The Upgrade:** Engineered an adaptive, dual-mode rotation engine using the tile's diagonal ($\sqrt{w^2 + h^2}$) as a threshold to prevent transparent corner clipping:
  * **Free Rotation Mode (Small Tiles):** If the image is larger than the tile's diagonal, the texture is rotated to a completely random angle ($0^\circ$ to $360^\circ$) using a stable, coordinate-seeded generator.
  * **Orthogonal Rotation Mode (Large Tiles):** If the tile is larger than the texture, rotation is restricted strictly to $90^\circ$ steps ($0^\circ, 90^\circ, 180^\circ, 270^\circ$), with the safety margins dynamically swapped to accommodate the rotated dimensions.
* **The Benefit:** Maximizes natural grain and veining variance across all tiles while ensuring zero background-bleeding or corner clipping on larger surfaces.
